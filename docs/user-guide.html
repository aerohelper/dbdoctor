What is dbdoctor?

Databricks Doctor is an open-source, read-only health-assessment CLI for Databricks workspaces. Point it at a workspace and it runs a catalog of configuration and operational checks against your clusters, jobs, and SQL warehouses — then reports what it found as a score, a console summary, a JSON payload (for CI/CD), or a standalone HTML page.

Not installed yet? See the Installation Guide first.

How authentication works

dbdoctor never asks for a workspace URL or a token on the command line. It uses the Databricks SDK's unified authentication: every command reads your credentials from the same place the official Databricks CLI writes them (~/.databrickscfg's [DEFAULT] profile), resolved automatically at startup.

This means: authenticate once with databricks auth login (see the Installation Guide), and every dbdoctor command — auth test, scan, anything added in future versions — just works against that workspace with zero flags.

Command: dbdoctor scan

The core command. Collects your clusters, jobs, and SQL warehouses once, runs all 14 registered health checks against that snapshot, computes a health score, and renders a report.

Examples

dbdoctor scan

Console report, printed to the terminal, using all default thresholds.

dbdoctor scan --format json --output report.json

JSON report written to report.json — ideal for CI/CD pipelines.

dbdoctor scan --format html --output report.html

Standalone HTML report you can open in a browser or attach to a Slack message / email.

dbdoctor scan --config dbdoctor.yml

Console report, but with your own thresholds from dbdoctor.yml instead of the built-in defaults.

scannedAt is always ISO-8601 (e.g. 2026-08-07T13:05:38Z), never a raw numeric timestamp — safe to parse with any standard date library.

HTML

A standalone, styled HTML page — no external stylesheets or scripts, so it's safe to email or attach as a CI artifact. It shows the score prominently, colored severity badges, and one table per resource category (Clusters / Jobs / SQL Warehouses) listing every check's title, description, and recommendation.

Open an HTML report in any browser — double-click the file, no server required.

Two checks the plan considered but deliberately excluded from v0.1: idle cluster and large warehouse with low utilization. Both would require Query History / System Tables usage data that isn't wired up yet — dbdoctor doesn't invent metrics it can't reliably compute.

Health score

dbdoctor's own opinionated 0–100 score — not an industry-standard metric. It starts at 100 and deducts per finding:

100 −15 × criticals −5 × warnings = score

INFO-level findings don't affect the score. The score never goes below 0. Both penalty values are configurable programmatically if you're embedding dbdoctor's scoring logic elsewhere, though the CLI doesn't yet expose flags for them (see Configuration file for what is CLI-configurable today).

Configuration file

Every check's threshold has a sensible built-in default, but you can override any of them with a YAML file passed via --config. You only need to specify the fields you want to change — everything else keeps its default.

Example — examples/dbdoctor.yml
checks:
  cluster:
    maxAutoTerminationMinutes: 120   # CLUSTER-002
    minSupportedRuntimeMajorVersion: 13   # CLUSTER-003
    maxWorkers: 10   # CLUSTER-005

  job:
    failureThreshold: 3   # JOB-002
    maxRuntimeMinutes: 180   # JOB-003

  warehouse:
    largeSizes:   # SQL-002
      - Large
      - X-Large
      - 2X-Large
      - 3X-Large
      - 4X-Large

Run with:

$ dbdoctor scan --config dbdoctor.yml

Minimal example — override just one threshold, everything else stays default:

checks:
  job:
    maxRuntimeMinutes: 60   # stricter than the 180-minute default
Only fields that map to a real, configurable check threshold are supported. Checks with no tunable parameter (e.g. CLUSTER-001 auto-termination disabled, SQL-001 auto-stop disabled) have nothing to put in the config file — there's no fake "enable/disable this check" flag yet.

Exit codes & CI/CD

Exit codeMeaning
0Scan completed, no CRITICAL findings.
1Scan completed, but at least one CRITICAL finding was found.

This makes dbdoctor scan directly usable as a CI/CD gate:

# GitHub Actions step — fails the job if any CRITICAL issue exists
- name: Databricks health check
  run: dbdoctor scan --format json --output scan.json

🛡️ Safety model

dbdoctor is entirely read-only in v0.1:

READ Databricks
      ↓
   ANALYZE
      ↓
    REPORT

It never edits a cluster, deletes a resource, changes a policy, or stops compute. Every Databricks SDK call dbdoctor makes is a list, listRuns, or me read — verified by inspecting every call site in the codebase. Safe to point at a production workspace without asking anyone's permission first.

❓ FAQ

Do I need to pass my workspace URL to every command?

No. It's resolved automatically from your Databricks CLI login (~/.databrickscfg). See How authentication works.

Can dbdoctor scan multiple workspaces at once?

Not yet — each run targets whichever workspace your DEFAULT profile points to. Multi-workspace support is on the long-term roadmap (v1.0), not the v0.1 MVP.

Does dbdoctor check Delta Lake or Unity Catalog?

Not in v0.1. The MVP scope is deliberately Clusters + Jobs + SQL Warehouses only. Delta Lake health, Unity Catalog, Spark performance, and cost prediction are all future roadmap items (see the README's Future Roadmap section).

Can I disable a specific check?

Not yet — all 14 checks always run. Per-check enable/disable is a natural extension of the config file but isn't implemented in v0.1.

Where do I report a bug or suggest a check?

Open an issue on the project's GitHub repository. Contributions are welcome — see the Contributing section of the README.
