Prerequisites

You'll need these installed before you start. dbdoctor has no other runtime dependencies — it's a single self-contained jar once built.

RequirementMinimum versionWhy
Java (JDK)21+dbdoctor compiles to the Java 21 language level. A newer JDK (e.g. 25) runs it fine.
Apache Maven3.9+Builds the multi-module project and produces the executable jar.
Databricks CLILatestUsed once, to authenticate. dbdoctor itself doesn't require the CLI at runtime — it just reads the credential file the CLI writes.
GitAny recentTo clone the repository.
You do not need a Databricks personal access token, and you never paste a token into dbdoctor directly. Authentication is handled entirely by the Databricks SDK's unified authentication, backed by a one-time browser sign-in via the Databricks CLI.

1 Verify Java & Maven

Open a terminal and confirm both are installed and on your PATH:

Snapshot — verifying toolchain
# check Java
$ java -version
openjdk version "21.0.x" ...

# check Maven
$ mvn -version
Apache Maven 3.9.x
Java version: 21.0.x, vendor: Eclipse Adoptium

If either command isn't found, install a JDK 21+ distribution (e.g. Eclipse Temurin) and Apache Maven for your OS, then re-open your terminal.

2 Clone the repository

$ git clone https://github.com/aerohelper/dbdoctor.git
$ cd dbdoctor

3 Build with Maven

dbdoctor is a multi-module Maven project (doctor-core, doctor-api, doctor-checks, doctor-report, doctor-cli). A single command builds and tests all of them, and packages an executable "fat jar":

$ mvn clean install
Snapshot — successful build
... compiling 5 modules, running 57 unit tests ...
[INFO] BUILD SUCCESS
[INFO] Total time:  12.4 s

The runnable jar lands at:

doctor-cli/target/dbdoctor-0.1.0-SNAPSHOT.jar

Every command in this guide (and the User Guide) assumes you run java -jar doctor-cli/target/dbdoctor-0.1.0-SNAPSHOT.jar <command> from the repo root. If you'd rather not type that every time, see the shell alias tip in Next steps.

4 Install the Databricks CLI

dbdoctor authenticates via the Databricks SDK's unified authentication, and the simplest way to set that up locally is a one-time login through the official Databricks CLI.

Windows 
$ winget install --id Databricks.DatabricksCLI -e
macOS 
$ brew tap databricks/tap
$ brew install databricks
Linux 
$ curl -fsSL https://raw.githubusercontent.com/databricks/setup-cli/main/install.sh | sh

Verify the install:

$ databricks -v
Databricks CLI v1.11.0

5 Authenticate

Run OAuth U2M (user-to-machine) login against your workspace. This opens a browser window for you to sign in — no token to copy anywhere.

$ databricks auth login --host https://<your-workspace-url> --profile DEFAULT

Complete the sign-in in the browser tab that opens. On success:

Profile DEFAULT was successfully saved
Use the profile name DEFAULT. dbdoctor's SDK client resolution reads the [DEFAULT] section of ~/.databrickscfg automatically — no environment variables or flags needed. If you log in under a different profile name only, dbdoctor won't find it without extra configuration (see Troubleshooting).

This writes a config file to ~/.databrickscfg (or %USERPROFILE%\.databrickscfg on Windows) — dbdoctor and the Databricks CLI both read it. You only need to do this once per machine; the CLI keeps your token refreshed in the OS keyring.

6 Verify the install

Run the built-in connectivity check:

Snapshot — dbdoctor auth test
$ java -jar doctor-cli/target/dbdoctor-0.1.0-SNAPSHOT.jar auth test

✓ Databricks authentication successful

Workspace: https://dbc-xxxxxxxx-xxxx.cloud.databricks.com
User: user@example.com
Status: CONNECTED

If you see CONNECTED, you're fully installed and authenticated. Head to the User Guide to run your first scan.

🔧 Troubleshooting

"~/.databrickscfg has no DEFAULT profile configured"

You authenticated under a named profile (e.g. --profile mycompany) instead of DEFAULT. dbdoctor's zero-argument client only reads the [DEFAULT] section. Either re-run databricks auth login --profile DEFAULT, or edit ~/.databrickscfg and add a matching [DEFAULT] section with the same host/auth_type values as your named profile.

"DEFAULT and <profile> match <host> in ~/.databrickscfg. Use --profile..."

You have two profiles pointing at the same workspace host, and the CLI-backed token source can't disambiguate. Remove the extra profile section from ~/.databrickscfg, keeping only [DEFAULT].

"ClientID cannot be null" / NullPointerException during authentication

This means no usable credential was found at all — most commonly because the databricks executable isn't on your PATH in the terminal session running dbdoctor (a fresh install sometimes needs a new terminal/shell session to pick up the updated PATH). Close and reopen your terminal, confirm databricks -v works, then retry.

Build fails with a Mockito / Byte Buddy error on newer JDKs

Very new JDKs occasionally ship faster than test-mocking libraries catch up. The project pins Mockito 5.19.0+, which supports JDK 25. If you're on an even newer JDK and hit this, bump the mockito.version property in the root pom.xml to the latest release.

"Access is denied" deleting target/ on Windows during a rebuild

A previous java -jar process is still holding files open (the SDK's background token-refresh thread doesn't always exit immediately). Close any running dbdoctor processes, or just wait a few seconds and retry mvn clean.

Optional: shorter command

Instead of typing the full jar path every time, add a shell alias:

# bash/zsh — add to ~/.bashrc or ~/.zshrc
alias dbdoctor='java -jar /path/to/dbdoctor/doctor-cli/target/dbdoctor-0.1.0-SNAPSHOT.jar'

# PowerShell — add to your profile
function dbdoctor { java -jar C:\path\to\dbdoctor\doctor-cli\target\dbdoctor-0.1.0-SNAPSHOT.jar @args }

The rest of this documentation uses dbdoctor as shorthand assuming this alias is set up.
